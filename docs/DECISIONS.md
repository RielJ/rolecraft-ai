# hanapbuhay: decisions and research

This file records every decision made during initial planning, and the research behind them. `PLAN.md` builds on it. Change a decision here first, then update the plan.

## Product

hanapbuhay is a local job-search workspace for a person based in the Philippines who applies globally, mainly to Philippine and US employers and clients. It finds postings, ranks them against the user's confirmed facts, tracks applications and contracts, and drafts tailored files and answers that use only those facts.

The first user is the author. A few friends will each run their own copy.

## Decisions

### Profile and facts

1. **One confirmed fact list.** The CV and the add-ons are both turned into facts. The user confirms each fact before it is used. Generated text may only use confirmed facts and cites them by id.
2. **Add-ons use one form with a type tag.** Types: experience, open source, challenge, other. Fields: title, what you did and the result, and optional date, link and skills. The app splits each add-on into facts for the user to confirm.
3. **Add-on usage setting.** Each add-on is usable either everywhere (the default) or in answers and letters only, never on the resume.
4. **Add-on links.** Replaced by 55 for GitHub links. Other links are stored only: they can be cited in generated text, and the app never fetches them.
5. **Profile input.** A CV file (PDF or DOCX) or pasted text. Portfolio items go in as add-ons. Reading a portfolio URL is later work.

### Jobs and sources

6. **Add a job by link, with a paste fallback.** The app reads the page once. If it gets too little text, the user pastes the description. This is how jobs from LinkedIn, JobStreet, Upwork and referrals get in.
7. **Eligibility verdict.** The question is "can I be hired from the Philippines?" Verdicts: open to PH, worldwide, region (APAC or Americas), excluded, unclear. Rules come first, and an optional AI pass handles unclear jobs. The UI shows the phrase that decided the verdict. "Excluded" is hidden by default.
8. **Working hours.** When a posting states hours or an overlap requirement, the job shows it converted to Philippine time. Filtering on hours is later work.
9. **Match level.** Strong, Possible or Weak, computed by rules from confirmed facts and preferences: title fit, skills matched and missing (the skills in confirmed facts, adjusted by the skills you add or hide, decision 66), seniority and years, eligibility. Each job lists its reasons.
10. **Duplicates.** Jobs with the same apply URL, or the same company and normalized title within a few weeks, merge automatically. Likely duplicates get a "possible duplicate" suggestion with a one-click merge. Board status and files stay on the merged job.
11. **Sync timing.** A Refresh button only. No timers or schedules. The top bar shows when the last Refresh finished ("Refreshed 3 days ago"), so a stale feed is visible (51).
12. **Own sources.** Built-in boards are on or off. Users can add company boards (Greenhouse, Lever, Ashby, SmartRecruiters, Recruitee, Workable) by careers-page link. The board is checked before it is saved.
13. **Keywords.** The target titles in the profile are the default search for keyword sources. Each source can override them with its own list.
14. **Dismiss.** Dismissing hides the job and takes an optional reason (wrong stack, too senior, pay, location, other). Reasons are stored but not yet used for ranking.
15. **Old jobs.** Jobs on the board, dismissed jobs, and jobs with files are kept forever. Untouched jobs closed for 60 days or more are deleted on Refresh. Excluded jobs follow the same rule; an override to Matches (53) does not count as touched. A sync never changes statuses, files, answers or notes.

### Opportunities and board

16. **Jobs and contracts share one board.** Each opportunity has a type: job or contract. Contracts add a rate, a rate type (hourly or fixed), a currency and a platform, and use "Proposal sent" in place of "Applied". Tracking active contracts (hours, invoices) is later work.
17. **Statuses.** Saved, Applied (shown as Proposal sent for contracts), Interviewing, Offer, and Closed with an outcome: Accepted, Rejected, No response, Withdrawn. Every change is logged with its date.
18. **Board extras.** Each opportunity has notes. An Applied opportunity with no change for 14 days shows a quiet "follow up or close?" hint.
19. **Contractor caution.** Contract opportunities show a short caution: "US clients usually need a W-8BEN; payment and tax setup come up at interview." The app tracks nothing about it.
20. **Pay.** Pay is stored as posted: min, max, currency and period. For display and filtering it is converted to a view currency. Rates fill automatically from public sources (decision 67); a rate the user types overrides them. Jobs with no pay stated show "not stated" and are never filtered out.

### Files and answers

21. **File set.** Tailored resume, cover letter, and short message. All three are ticked by default and the user can untick any per job. The short message also covers contract proposals.
22. **Formats.** Files are edited in the app. The resume and letter export to PDF from one template. Any file can be copied as text.
23. **Questions.** The user types questions in. The AI suggests questions it finds in the posting's text. The app never reads application forms.
24. **Must-answer questions.** Salary, visa or work authorization, notice period, start date and references are detected and never drafted. They are filled from reusable answers in the profile and can be overridden per job.
25. **"Needs your input" gate.** A job cannot be marked ready, and final files cannot be exported, while it still has unanswered must-answer questions or placeholders. The job page lists exactly what to fix.
26. **Outdated files.** Each file and answer records the facts it used. When any of those facts change, it shows "outdated" with the changed facts listed. It is regenerated only when the user asks. Jobs marked applied stay frozen.
27. **Never submit.** The app never submits applications or fills forms on other sites. This is a stated non-goal.

### Users, AI and cost

28. **Users.** v1 is single-user and has no login. Each person runs their own copy with their own database and their own AI key. Tables carry a user id so that accounts can be added later. Running only your own data falls under the personal-use exemption in RA 10173.
29. **AI providers.** Anthropic or OpenAI, using an API key the user pastes into settings, behind one small interface.
30. **Model choice.** AI work is split into two tiers. The light tier covers fact extraction, eligibility checks and finding questions in postings. The writing tier covers the resume, letter, message and answers. Each tier has its own model setting. The default is the cheapest model that passes a small evaluation set: no invented claims and no missed exclusions.
31. **Spending.** Each AI call records tokens and estimated cost. Settings shows this month's total, and an optional monthly cap asks for confirmation before going over it. AI runs only when the user clicks, except the optional eligibility pass on unclear jobs during Refresh.
32. **Retrieval.** No vector search in v1. Every draft gets the whole confirmed fact list. Jobs are searched with Postgres full-text search. pgvector can be added later if the fact list outgrows one request.

### Stack

33. **App shape.** A Vite React SPA (TanStack Router and TanStack Query) and a Hono API. In production one Bun process serves both.
34. **Database access.** Drizzle, with SQL migrations generated from the TypeScript schema.
35. **Postgres.** Docker Compose runs Postgres and the app for everyone.
36. **Long tasks.** Tasks run in the same process and are recorded in a `tasks` table (kind, status, current step, error), which the UI polls. On restart, unfinished tasks are marked interrupted and offer a retry. Every task goes through one `startTask`/`getTask` module, so pg-boss can replace it later.
37. **Tooling.** Bun, Biome, `bun test`, and Playwright for a few end-to-end flows.

### UI

38. **UI kit.** shadcn/ui, Tailwind and lucide icons. Every screen is built with the `design-engineering` skill, following its craft floor and refusing the generic template patterns it lists. Components use the `shadcn` skill. The goal is that it does not look like a generic AI-built app.
39. **Theme.** Replaced by 50.
40. **Job view.** Matches is a list with a reading pane, navigated with the keyboard. The workspace (files, questions and answers, apply checklist) is a full page.
41. **Navigation.** A slim top bar: Matches, Board, Profile, Sources, with Settings and Refresh on the right.
42. **First run.** A setup checklist on the empty screens: AI key, CV, confirm facts, preferences, sources, first refresh. Steps can be done in any order. There is no wizard.

### Added while synthesizing the plan (`docs/PLAN.md`)

43. **Natural writing.** Outputs must read as if the user wrote them. The prompt carries voice rules (plain first person, no em dashes, no AI-tell phrases). A style check flags leftover tells, makes one targeted rewrite, and shows anything left as an editor warning. Warnings don't block export. `[FACT-n]` markers appear only inside the app. PDF and Copy as text never contain them.
44. **Role filter.** Every source, company boards included, sorts titles into role families. A sure out-of-family title or one with an exclude word is dropped at sync. Mixed or unknown titles are kept and tagged "Role unclear". In-family titles are kept. When in doubt, the job is kept. Dropped titles are stored as slim rows and shown on the Board (53).
45. **Sources in setup.** All five built-in sources are on by default. The first-refresh step of the setup checklist lets the user turn each one off before the first sync.
46. **Exact-match merge (narrows 10).** A job is merged automatically only when it is the same posting: the same apply URL and title, or the same company, title and description within 28 days. The same company and title alone is only a "possible duplicate" suggestion. Feeds close a job after 30 days without a sighting.
47. **Other plan defaults confirmed:** services call Drizzle directly, and the `hb_sync` Postgres role enforces the sync rule. PDFs come from headless Chromium. The AI key is stored in a 0600 file, not in Postgres. Sites that forbid automation go straight to the paste form. A deleted cited fact blocks the gate. Copy as text is gated. Applied outputs are read-only. A CV re-import is compared line by line, and the app asks before removing a fact. FX rates are typed in per currency.
48. **Local pi runner (extends 29).** The API key in Settings stays the default. A local copy can set `HB_AI=pi` instead: the server then runs each AI call through the `pi` CLI on the same machine, using pi's own sign-in, so no key is pasted or stored. pi runs with no tools, extensions, skills, context files or prompt templates, and with the app's own system prompt. That keeps the app's prompt as the only input and cut the overhead from about 6,800 to 68 tokens per call when measured. The writing tier defaults to Claude Opus 5.5 and the light tier to Claude Haiku 5.5. Thinking is off for light calls and low for writing. Each call records the tokens and cost that pi reports, so spending and the cap still work. On a pi subscription that cost is a list-price estimate, not a bill. pi is not in the Docker image, so `HB_AI=pi` is for running the app directly on your own machine.
49. **CV text cleanup and contact from the CV (extends 9 and the Profile in section 4).** A PDF's text keeps the page's line breaks, so the reader joins lines the page wrapped and drops bullet glyphs that sit on a line of their own. It never changes, adds or reorders a word. Pasted and DOCX text is left as is. Saving a CV also reads its first eight lines for a name, email, phone, location and links, and fills only the contact fields that are empty. A field the user filled is never overwritten; the default `Philippines` counts as empty and is kept after a city. Both steps are rules, not AI, so they cost nothing and every value they produce is text from the CV.
50. **Dark brand look (replaces 39).** One warm dark palette with an orange accent; the app no longer follows the OS light setting. Geist is the UI and heading face, with large light page headings, and the reading surfaces keep the serif. Glow and glossy surfaces are kept to brand moments: the primary button, the top bar, the setup checklist, empty states and dialogs. The working screens (the Matches list, the reading pane, the board and the workspace editor) stay flat, so long reading is not competing with light. A disabled primary drops its glow and goes flat grey, because a dimmed glow reads as brown, not as "not yet". The craft spec's axe contrast check guards the palette.
51. **Success measure.** The app is judged on interview rate: applications that reach Interviewing over applications sent. Time from Saved to Ready is the early signal. The baseline is rebuilt by hand from the two months before real use. The app is for one person until it has produced interviews; install polish and friend onboarding wait until then. Day to day it runs on the host with `HB_AI=pi` and Postgres in Docker. Backups are out of scope by choice: losing the volume means re-importing the CV.
52. **Metrics line.** One quiet line on the Board for the last 30 days: applied, reached Interviewing, the rate, and the median Saved to Ready time. Saved to Ready includes idle time, so it is an upper bound. The numbers come from the dated status history; no new table.
53. **Filtered-out postings.** Matches shows a count on its Excluded toggle. The Board has a collapsed "Filtered out" section with two kinds of item. Excluded jobs are real jobs whose eligibility rule said no. Role drops are slim rows (title, company, link, source, the word that dropped them), replaced for a source on each of its runs, so they stay bounded by feed size. Items are grouped by reason; each group shows its newest 50, and a search box finds the rest. An excluded job can be overridden to Matches; the override lives in a user-owned table the sync role cannot write, so no sync undoes it. A role drop offers Add by link with its URL filled in.
54. **Fact strictness stays.** Drafts use only confirmed facts and the gate still blocks export. When drafts are thin, the fix is cheaper fact entry (55), not an unverified tier or an override.
55. **GitHub add-ons (replaces 4 for GitHub).** An add-on can take a GitHub repo link (a side project) or a pull request link (a contribution). The app reads, within a hard token cap: the README, the manifest, the file tree, up to five files the light-tier AI picks from the tree, and the user's last 50 commits on the repo. Reads use the public API by default. With `HB_GITHUB=gh` they go through the local `gh` CLI, pinned to `HB_GITHUB_USER`; a call is refused when gh's active account differs, so a work account never leaks in. The app never reads gh's token, and Docker stays public-only. Repo text is passed to the AI as data, never as instructions. Each proposed fact links the file or commit it came from, and the user confirms each one as with CV facts. Facts from private repos carry a lock badge; their text may be drafted from, but a private repo or commit URL never appears in an exported file. A manual Re-read compares new proposals with the current facts like CV re-import (47). Three recorded fixture repos join the evaluation set, one with a README that tries prompt injection; the pass mark is zero invented claims and zero injected facts.

### Chrome extension (`docs/plans/chrome-extension.md`, `docs/EXTENSION.md`)

56. **Local hardening instead of a login (Task 0).** The app still has no login. The server listens on `127.0.0.1` by default (`HB_HOST`), and the Docker image listens on `0.0.0.0` while Compose publishes the port on `127.0.0.1` only. A request whose `Host` is not `localhost`, `127.0.0.1`, `[::1]` or a name in `HB_ALLOWED_HOSTS` gets 403, which blocks DNS rebinding. An `/api` write with a foreign `Origin` or `Sec-Fetch-Site: cross-site` gets 403 `forbidden_origin`, which blocks CSRF from other sites. `/api/extension/*` skips the Origin rule and needs a bearer token from pairing instead. A login would protect against other users of the same computer, which a one-person local app does not have.
57. **Session lifetimes.** An application session from **Apply** stays pending for 15 minutes, the time to open the panel on the new tab. A claim extends it to 4 hours from the first claim, the time to fill a long form. A second claim by the same pairing does not extend it again. A new **Apply** expires the live session, so at most one is live. A pairing code lasts 10 minutes and works once.
58. **Edits clear the reviewed state.** A generated answer or file fills a form only after the user marks it reviewed (`outputs.reviewed_at`). A redraft clears the mark, and so does any body edit through `PATCH /api/outputs/:id`, from the web editor as well. The plan let web edits keep the mark. The code is stricter because the reviewed text is the text that fills a form, and an edit can change it. The cost is one extra **Mark reviewed** click after an edit.
59. **`combobox` control type.** A type-ahead widget (`role=combobox` with a list popup, such as Greenhouse's react-select questions) has its options outside the page until the user types. Typing text into it selects nothing. The scan reports these fields as `combobox`, the matcher leaves them blank with `unsupported_control`, and the review lists them under **Left blank**, so the user sees what to fill by hand.
60. **Positional option tokens.** When two options of a select share a value, or radios have no `value` (Ashby's EEOC questions), the page's values cannot name one option. The scan then offers every option of that control as `opt:<index>`, and fill writes the element at that position after it checks the field's signature. Otherwise the scan offers the page's own values.
61. **Blocked sites (open question).** The current behaviour follows the plan's default. On the hosts in `src/shared/hosts.ts`, the extension never reads, scans, fills, attaches to, or checks a page for success, and the panel's import refuses to read the page. Jobs from those sites still get in through the web paste form and the server's import route. **Apply** still opens them, and the panel can link the tab to the session when it can read the tab's address. The panel does not show answers as text to copy; the workspace's **Copy as text** does that. **Open:** should prefill be allowed on these sites? JobStreet's §9(b) bans "any automated process, script, tool", and the others forbid automated access too. Prefill runs on the user's click, so the user has to decide whether that counts.
62. **Facts are grouped by job.** Each fact stores a `section`: the employer, project, school or heading it sits under, copied from the item's text. The AI split returns it with each fact, and the rule splitter takes the short line above a run of bullets, or else the latest heading. A section is kept only when the item's text contains it word for word, so a label cannot invent an employer; otherwise the fact shows ungrouped. On the Profile page, confirmed facts are grouped by section (an add-on fact with none falls back to the add-on's title). Past 8 confirmed facts the groups start closed, and a search opens every group with a match. A re-split sends the item's saved facts to the AI, which reuses their wording where the text still says the same thing, so splitting again to add sections keeps confirmations.
63. **Skills lines are facts, and skill coverage orders each level.** Matching reads skills from confirmed facts (and from the skills you add or hide, decision 66), and the split prompt used to skip a CV's skills section, so a CV that lists "PostgreSQL, Redis" there matched as if it did not. The split prompt now keeps every skills line as one fact, worded as the text has it, and the fact checker accepts it like any other line. Within a level, Matches now sorts by the share of the posting's skills your facts name, then by how many, then by newest; before, a level was newest first. Each row shows "N of M skills". The levels themselves do not change: coverage only decides order within Strong, Possible and Weak.
64. **Matches has two layouts, and three ways to act on a job.** "List" shows the list beside the job. "One at a time" shows one job across the frame, with the posting kept to a reading width, the job details in a column beside it, and a pager ("12 of 219 · Possible"). The arrow keys, j/k and the pager move between jobs, and L switches layouts. Matches opens in the layout used last, stored in the browser. A job can be acted on three ways. **Start application** (Enter) saves it and opens the workspace; the workspace then shows **Next match**, which returns to the job after the one started. **Save for later** (S) saves it and moves on, with Open and Undo in the toast. **Save and write files** (Shift+S) saves it, starts the draft task in the background, and moves on, with no undo because the files are already being written. The Board card shows "Writing files…" while the draft runs and "Files failed" if it fails. Why: saving used to remove the job from Matches with no way to keep working on it except the Board, and opening it was a hidden key.
65. **Matches filters by company and source, and can hide a company.** The Company filter matches `companyKey`, so "Acme" and "Acme Inc." are one company, and picks several at once. The Source filter picks company boards, job sites, jobs you added, or one job site. Both run on the server before the 500-job cut, and each choice shows how many jobs picking it leaves, counted with the other filter on. "Hide all from {company}" (`d` then `h`) hides every job from that company until you show it again. Hidden companies are stored per user in `hidden_companies`, which the sync role cannot read or write. They stay in the Company filter, marked, and picking one shows its jobs. The bottom bar counts the hidden jobs, and clicking that count opens the list with Show buttons. The filters are not saved between visits; hidden companies are.
66. **You can add skills to matching and hide them from it, and the dictionary knows more skills.** Profile → Facts shows "Skills used for matching": the skills found in confirmed facts, plus the skills you add, minus the skills you hide. You add a skill from the dictionary or type one of your own, up to 100; you hide a skill that a confirmed fact names (a skill no fact names can only be removed). The list is stored per user in `user_skills`, one row per skill, which the sync role cannot read or write. Drafting never reads it: a draft still cites only confirmed facts, so a skill you add is never claimed for you. A skill of your own is read from job text like a built-in one, matching its exact case at 3 characters or fewer. Jobs are read with your list when added, pasted or imported. Adding or removing a skill of your own changes stored jobs at once, and a Refresh reads again only the open jobs read with another list or dictionary version ("Reading skills in stored jobs"; decision 68). Refresh loads your list as the app role before it starts. The dictionary grew from 76 to 108 skills: 9 from real CVs, 11 frequent in postings, and 12 candidates found in at least 5 open jobs. Names that are also ordinary words use strict patterns: "Spark" does not count at the start of a sentence or before "Capital", "Foundry" not after "Palantir", "Jest", "RAG" and "Bash" match their case only. Title fit also reads "Fullstack", "Frontend" and "Backend" as two words and "developer" and "programmer" as "engineer", and drops a title's tail after a dash, bar or bracket; dedup's `title_key` keeps the title's own words. Why: a CV with "Solidity" or "Nginx" matched as if it did not, and a skill named in an old fact could not be left out of matching.
67. **Exchange rates fill themselves.** Rates come from the ECB's reference rates, read through Frankfurter, with EUR as the base and crossed to the view currency, so USD to PHP is PHP per EUR over USD per EUR (62.9681, not the 4-digit 62.972 that a PHP base gives). Currencies the ECB does not publish, such as VND, come from currency-api (jsDelivr, then its pages.dev mirror). Rates are kept to 6 significant digits. **Fill rates** in Settings fetches now. Each Refresh ends with a fill when one is due: when a needed currency has no rate, 20 hours after the last good fetch, or 1 hour after a failed one; a currency no source publishes is remembered and does not reopen the gate. Needed means the pay currencies of open jobs, the min pay currency, and every rate already fetched. A rate the user types is never overwritten; removing it hands the currency back to automatic updates. A failed fetch keeps every existing rate, never fails the Refresh, and shows under Rates with its error. Changing the view currency still clears the rates, and its toast offers Fill rates. The fill runs as the app role after the sources, never as the sync role, and the last attempt is stored in `users.fx_fetch`. No AI is involved. Why: with jobs in nine currencies, every rate was typed by hand and went stale.
68. **Skill edits apply at once, and Refresh reads only what changed.** Adding a skill of your own updates stored jobs inside the `PUT /api/profile/skills` request, as the app role, in one transaction with the skill row. Postgres keeps the open jobs whose `lower(title || description)` contains the skill's longest piece without spaces (one per spelling), and the exact regex decides on those. Removing a skill takes it off every job with `array_remove`. Adding or hiding a built-in writes no job; hiding stays a read-time filter. Each job stores `skills_stamp`: the built-in version (`BUILTIN_SKILLS_VERSION`) and a hash of your own names. A Refresh reads again only open jobs whose stamp is not the current one, so a Refresh where nothing changed reads none, and bumping the version reads every open job once. An add or remove moves the open jobs that held the old stamp to the new one. It takes `MERGE_SYNC_LOCK` exclusive, so no sync write lands between reading the jobs and stamping them. A Refresh already running when you add a skill saves its jobs with the old stamp, so they miss the skill until the next Refresh reads them. `extractSkills` lowercases a text once and skips each regex whose piece the text lacks; a test shows the output is the same with the check on and off, and on the dev database's 1,978 open jobs it was the same for every job and cut the read from about 1 s to 0.3 s. The lowercasing (`foldCase`) also maps the 22 characters, such as ſ and ς, that a case-insensitive regex folds but `toLowerCase` does not; a test checks every code point. Postgres' `lower()` does not map them, so a job that spells a skill with one of them is found by the next Refresh, not by the add. `jobs` keeps half of each page free (`fillfactor = 50`, migration 0014, so the CV preview plan moves to 0015). No index covers `skills` or `skills_stamp`, so with room on the page their updates are HOT: Postgres writes no new `jobs_search` entry for every word of the job. Moving the stamp on 1,993 dev jobs took 250 to 400 ms at fillfactor 100 and 5 to 8 ms at 50. Budgets, asserted on 2,000 jobs of 8 KB with real-sized search vectors: adding a skill takes at most 300 ms end to end, and the re-read step of a Refresh where nothing changed at most 100 ms. On the dev database, after one slow first add (518 ms) that moved rows to half-full pages, an add took 97 to 118 ms (the substring scan is 73 to 79 ms of it), a remove 21 to 25 ms, and the unchanged re-read 2 to 10 ms. The plan used `jobs.search @@ phraseto_tsquery(...)` to narrow the jobs, assuming it returns every job that might match. It does not: of 6,936 job-skill matches in the dev database it missed 397 (5.7%), mostly because the parser keeps slash-joined words as one token ("React/Redux", "Power BI/Tableau", "x.com/temporal"). If open jobs grow past about 6,000, a `pg_trgm` trigram index on the same lowercased text is the next step. Aho-Corasick is held in reserve for when the regexes miss a budget. pgvector does not help: embeddings measure likeness, not whether a posting names Kubernetes. Why: a skill you add should show on Matches when you add it, and every Refresh spent about 1 s reading 2,000 unchanged jobs.
69. **A PDF CV is kept so you can view it.** Uploading a PDF of 5 MB or less stores it in `cv_files`, one row per user, and a new one replaces it. A DOCX, a PDF over 5 MB (still read, up to 10 MB), or pasted text that differs from the stored text deletes it; saving the same text keeps it. An upload that cannot be read changes nothing. The table takes only `application/pdf`, from 1 byte to 5 MB, and its size column must match the bytes. The sync role cannot read or write it. The profile carries the file's name, size and upload time, never its bytes. `GET /api/profile/cv/file` serves it inline behind `localGuard`, and refuses `Sec-Fetch-Site: cross-site` with 403, since `localGuard` checks Origin only on writes. Its type is always `application/pdf`, with `nosniff`, `no-store`, `Cross-Origin-Resource-Policy: same-origin` and `X-Frame-Options: SAMEORIGIN`; a name with quotes, newlines or non-ASCII is sent as an ASCII `filename` plus an exact `filename*`. It sends no `sandbox` CSP, because Chrome's PDF viewer refuses to render under one. Profile → CV shows "Last read from x.pdf · View". View opens a dialog with a PDF tab (the browser's own viewer in an iframe) and a Text tab (the text the facts came from). From 1024 px the CV's facts sit beside the tabs; narrower, they get a Facts tab. With no kept file there is only the Text tab, and a DOCX says "Word files show as the text the AI read." Why: users could not check what was read against what they uploaded.
70. **Files show as files, never as fact-marked text.** Nothing the user sees as a file shows `FACT-n` keys or Markdown. The resume tab is a card with a status line (when it was drafted, its word count, how many blanks are left) and Preview PDF, Copy text and Download PDF. Edit text and Regenerate sit in an overflow menu. The letter adds its clean text, read-only, below the card. Messages and answers show clean text with Copy, and have no PDF. Preview opens a dialog that holds only the PDF and works while blanks remain, showing each blank as a highlighted box. Copy and Download stay locked until no blanks remain. Copy gives content only: headings become plain lines, bullets become `•`, and bold markup is dropped. The PDF and the copy drop a first `# ` line that repeats the contact name. Blanks get their own inputs under the card, applied together by one Save answers button. A missing-info blank has "Also save to my facts", ticked by default, which adds the answer as one confirmed fact ("question: answer", no AI split) to an `other` add-on named "Filled in while drafting". A Check this blank is pre-filled with its sentence: saving keeps the edited text as the user's own words, and Remove drops it. Edit text shows the text without markers; on save, unchanged sentences keep their sources and rewritten ones lose them. No page count is stored. A resume over 400 words gets "Likely over one page" (`RESUME_ONE_PAGE_WORDS`): a bullet-heavy draft fit 343 words on page one of the PDF template, and the user's own two-page CV averages about 400 a page. Preview PDF shows the real length. A stored count cost a Chromium render on every save, a background queue and polling, to answer what Preview already answers. Applied jobs keep Preview, Copy and Download only. The per-file cited-facts list is gone; the Facts changed warning and the facts rail show no keys. Why: a hiring manager cannot see our facts, so keys mean nothing outside the app, and a resume is used as a file, not read as text. Design in `docs/plans/clean-files.md`; drafting rules in `src/domain/drafting-guide.md` (decision 72).
71. **Resume roles are records, and the server writes their headers.** A role (title, company, location, start, end) is read from the CV or an experience add-on in the split task, and kept only when the text has its header: the title and the company must each start a part of a line (after the line start, a separator or "at") in one header block, up to four lines with no bullet text or section heading. The location and dates are kept only when that same block has them. So a company named in a bullet, a title cut out of a longer one, or one role's dates on another are dropped. In a resume draft, a sentence under a role header may cite only facts of that role, and nothing cited sits under Experience before the first header (`wrong_role`, retried). Roles are matched by key, never by date: overlapping roles are normal and keep the CV's order. A split candidate made only of one role's fields and separators ("Software Engineer, Jan, 2023 – Present") is not kept as a fact, since the role already holds it; the split prompt says to skip such lines, and the roles just read, or the item's saved roles when that read fails, decide. Known limit: one-line roles listed back to back with no bullets between them can still pair a title with the next line's company; the user corrects that on Profile. Roles live in a `roles` table (migration 0016) and are editable on Profile; facts link to a role by `role_id`, set when a fact's section matches exactly one role's company. Existing CVs read roles only when the user clicks "Read roles from your CV". The resume prompt lists the roles; the model writes `[ROLE-n]` on its own line, and the server replaces it with `### Title | Company, Location | Start – End` before the check, which skips those lines. An unknown role key is the violation `unknown_role`. Why: the split kept only the company name as a fact's section, so drafts had no titles or dates, and a header the model types could invent or misspell either. Design in `docs/plans/roles.md`.
72. **The drafting guide is part of every draft prompt.** `src/domain/drafting-guide.md` is read at import and split on its `##` headings. Every draft, retry and style rewrite sends "Facts and limits", "Tailoring to the posting", "Shared rules" and "Sounds like a person", plus the section for its kind: "Resume", "Cover letter", "Short message (job)" or "(contract proposal)", or "Application answer". Source references are stripped, and "How this guide is used", "Disagreements and our picks" and "Sources" are never sent. A missing or empty section throws, and a test checks every kind against the real guide. The guide lives in `src/domain` because the runtime image copies that folder and not `docs/`. The guide adds about 800 to 1,400 input tokens per call (a resume is the largest), and the spending-cap estimate counts them, since it is built from the whole prompt. A resume has no pronouns: its voice rule and marker example start with the verb, while the other kinds stay in first person. The resume task no longer asks for a `# name` heading; it names the guide's section order (Summary, Skills, Experience, Projects, Education). Three style rules join the existing ones and feed the same single rewrite: `pronoun` (resumes only: I, my, me, we, our and their forms, where "I" must be a capital so I/O never matches), `repeated_opener` (any kind's `-` bullets: a third use of one opening word under one heading, or any use past max(3, a quarter of all bullets); bold-labelled bullets and pronoun openers are skipped) and `same_shape` (four or more bullets, more than half ending in a ", cutting …" style clause; including, using, covering and spanning do not count). Why: drafts were reworded fact lists in first person, because the guide was a document the code was meant to follow and nothing made it. Design in `docs/plans/tailored-drafts.md`.
73. **A draft is tailored from a requirement map.** Before the first draft for a posting, one writing-tier call lists the posting's requirements (must, duty or nice), the confirmed facts that prove each, and one context fact per role. Unknown fact keys are dropped, and a requirement left with no facts is a gap the draft never mentions. The map is stored on the opportunity under a hash of the posting and the confirmed facts, so a redraft reuses it until either changes. A resume is drafted only from the facts that prove a requirement, plus each role's context fact and every fact with no role; letters, messages and answers get the same requirements but keep all their facts. Each kind sees only the fact keys it may cite. If the map reply is unreadable after one retry, the draft goes ahead from every fact and the next draft tries again.
74. **A resume never drops its strongest evidence (amends 73).** A role that proves any requirement keeps all its facts, since one strong bullet often combines several atomic facts and the map can miss one; a role that proves none keeps its context fact. Every fact that proves a requirement, and every fact with a number, in a matching role is REQUIRED: the prompt lists them, and a draft that leaves one out is retried once with the missing keys named (still missing after that is accepted). The prompt asks for related facts of one role to be combined into one bullet, and for the Summary to open with the posting's role noun where the facts show that work. The map prompt reads every list in the posting, splits compound qualities into separate requirements, and names which kinds of work prove performance, reliability, security and maintainability.
75. **A resume is tailored from the base CV (amends 73/74 for resumes).** When an imported CV parses into usable lines, the resume starts as that CV and the AI may only propose bounded changes: rewrite the Summary, reorder bullets inside a role or the skills lines, reword a bullet in the posting's terms when it already proves the requirement, remove a line the posting does not need, or add a bullet from a confirmed fact. Each change carries the requirements it serves, is checked against the line it replaces plus its cited facts (no new tool, number or name, no pronouns), and applies until the user undoes it; the body is always the base plus the changes not undone. A line whose facts are REQUIRED under 74 cannot be removed. Formatting is normalized (wrapped lines joined, bullet glyphs become "- ", role headers come from the roles table) but wording on unchanged lines is the user's own. Letters, messages and answers, and resumes with no usable CV, keep generating from facts; an unreadable reply leaves the CV unchanged rather than falling back to the generator. Why: Jobscan, Teal and Resume Worded all edit the user's resume rather than rewrite it, and Bloom measured unconstrained tailoring inventing about one claim every three runs against 0 in 106 bullets when grounded in the source resume and verified.
76. **Matches counts required skills and shows a percentage (amends 26 and 63).** A posting's nice-to-have text is found by rule: a section under a heading such as "Nice to have", "Bonus points" or "Preferred qualifications" (its list, or one paragraph when it has no list, up to the next heading or prose), a line labelled "Preferred: …", a line tagged "(preferred)" or "nice to have", and the clause a "… is a plus" closes (back to a semicolon, a dash, an open bracket or a "required,"). A skill named only there is nice to have and is stored in `jobs.nice_skills`; a skill also named anywhere else, the title included, is required. Only required skills decide the Weak threshold and the order within a level. A missing nice-to-have skill is a neutral reason, and one you have is positive. A posting whose every skill is nice to have counts them all as one list. The list row shows the share of required skills as a percentage ("67% required skills", or "88% skills" when the posting has no nice-to-have skills) once there are 3 or more, and the count ("1 of 2 skills") below that, so a one-skill posting never reads as 100%. The exact count is the row's tooltip and screen-reader text, and the reading pane shows it with the nice-to-have count ("2 of 3 required skills · 0 of 2 nice-to-have"). An added skill of your own is sorted into the same lists at once (decision 69). A change to how nice-to-have text is found needs a `BUILTIN_SKILLS_VERSION` bump by hand, since the dictionary fingerprint does not cover it. Measured on 2026-10-20 against the 1,999 open jobs: 388 have nice-to-have skills; 892 name 3 or more skills and get a percentage; 317 of those change, 32 cross from under 60% to 60% or more, and 19 leave Weak's under-30% zone. Why: a missing Kafka under "Nice to have" counted as much as a missing Node.js under "Requirements". A requirement percentage needs AI (slice F in `docs/plans/tailored-drafts.md`); this one is free.
77. **A project always shows its name, link and what it is (amends 75).** In the Projects section a project starts at a text line right after the heading or after a bullet, and the text lines under it (a link, a stack) belong to it until its first bullet. Tailoring may remove a project's bullets but never its last one: the prompt marks a project's only bullet (keep), and a remove that would take the last one is dropped as `only_description`, which alone does not trigger the retry. In the PDF a project's first line is bold, its other head lines (a link, a stack) use the smaller muted style of a role's company line, and the head sits as close to its bullets as a role header does. A line that is only an http(s) URL becomes a link shown without its scheme, `www.` or trailing slash. Why: a tailored resume removed two projects' descriptions and left their names and URLs as bare lines, and with no bullet between them the PDF could no longer tell a name from a link, so only one of them was bold.
78. **The app finds your projects; you pick which to add (amends 55).** With `HB_GITHUB=gh`, Profile lists the repos `HB_GITHUB_USER` owns (never an organization's), private ones included, through the local gh CLI; a scan on any other active gh account is refused, and without gh the option is hidden. Rules, not AI, suggest which to show: forks, the profile README repo and repos under 5 KB go to a collapsed "Hidden by rules" group with their reasons, where the user can still pick them; each group is ordered by last push, then stars, and nothing is remembered between scans. Repos an add-on already links show as Added. Each picked repo becomes an `open_source` add-on with its name, link, main language and description, split into facts like any add-on; Read from GitHub stays a separate click per add-on. The server lists again before adding and adds only names it found, and a private repo is marked private when added. Why: projects reach drafts only as add-ons, and adding each by hand meant most were never added. See `docs/plans/project-detection.md`.

79. **Find my projects also looks in a local folder (amends 78).** With `HB_PROJECTS_DIR`, the dialog also lists that folder's subfolders, one level deep. It shows them first: they hold work that isn't on GitHub yet. Commits by `git config --global user.email`, `HB_GIT_EMAILS` or the `HB_GITHUB_USER` noreply address count as yours; an author without an "@" counts as no one. Folders that aren't git repos, repos with fewer than 5 of your commits, and repos where fewer than half the commits are yours go to the hidden group. A clone of a repo in the gh listing shows once, under GitHub, with your local commit count; at least 5 of your commits keep that repo out of "nearly empty", and its README paragraph stands in for a missing GitHub description. An added folder takes its README's first paragraph as its text, or "<name>, a <language> project." when the README is missing or generator boilerplate. It gets a link only when its remote is your repo and no gh listing contradicts it, and that link stays out of exports until a read shows the repo is public. Git runs without a shell and reads nothing that can start a program (fsmonitor off, no index); symlinks are not followed. One source failing shows its error; the other still lists. Why: 4 of the user's 25 folders, including this app, are on no GitHub account, so the gh listing alone missed the newest work.
80. **One project can fill the add-on form.** The add-on form, when adding, has a "Fill from a project" field. It takes a GitHub repo or pull request link, a GitLab project link, or a folder path starting with `/` or `~`. It reads the project and fills the title, text, link and skills, with Open source as the kind; nothing is saved until the user saves the form. GitHub goes through the configured reader, so private repos work with `HB_GITHUB=gh`. A repo takes its description or README paragraph, as in decision 78. A pull request takes its title and the first paragraph of its description. A repo someone else owns gets a note asking the user to say what they did. GitLab is read through the unauthenticated REST API, on gitlab.com and on hosts in `HB_GITLAB_HOSTS` only, so a pasted link never makes the server call a host the user did not list. Private GitLab projects get a clear error, and reading GitLab code for facts is not built. A folder can be anywhere on the machine: the user chose no path limit. The server binds to 127.0.0.1 by default, and the local guard refuses other Host headers and cross-site requests. It is read and judged by decision 79's rules, and a folder those rules would hide gets a note saying why. A link from a private repo, or from a folder remote whose visibility is unknown, is saved with `githubPrivate` set, so it stays out of exports until a read shows the repo is public. That flag is sent only while the link field still holds the filled-in link. Why: the scan (78, 79) finds the user's own repos, but work in other people's repos, on GitLab, or outside `HB_PROJECTS_DIR` had to be typed in by hand.
81. **Reading a project for facts: features from your own changes.** Applies to local folders and GitHub repos; a deep read of GitLab waits. Your commits are those whose GitHub login is yours or whose email is in git config, `HB_GIT_EMAILS` or your noreply address, the same identity as decision 79. A project counts as yours when at least half its commits are yours; below half it is a contribution. In both cases feature facts come only from your commits. In your own project, the README, manifests and picked files may also describe what the project is and its stack. The read lists every commit of yours with its subject and its changed files with +/- counts. The light model reads the README and that list, groups the commits into up to 6 features, and picks 2 or 3 commits for each. The hunks of those commits are read, trimmed first when the 12,000-token cap (decision 55) is tight, and each fact covers one feature and cites its commits. Hunks come from a local clone when the folder scan found one, which includes unpushed work. Without one, they come through the API when `HB_GITHUB=gh`. Otherwise the app makes a temp clone (`--filter=blob:none`, a 2-minute timeout, deleted on every exit path). A repo over 500 MB is never cloned: the API gives hunks for 10 of your commits, and the rest stay subjects and file lists. Local code is treated like a private repo: its text may be drafted from. `.env*`, `*.pem`, `*.key`, `id_*`, credentials files and anything git ignores are never read. A folder is public only when its GitHub or GitLab remote answers without login, checked at each read; then its pushed commits get links. A private project's facts show only the project name. The cited sha or path is stored, so the citation check and re-read work, but it is never shown or exported. Find my projects has a "Read each project for facts" checkbox with the estimated cost. Its reads run one at a time in the background, and the spending cap is checked once for the batch. The Fill form has a "Read for facts" checkbox, on by default after a fill, and it works for folder paths too. A re-read compares new proposals with the current facts, as decision 47 does. A new fact is left out when a fact staying on the add-on, from its own text or an earlier read, or an earlier fact of the same read already says 80% of its content words and every number in it, the same test tailoring uses for a repeated bullet. Why: the shallow add-on text said what a project is, not what the user did in it, and commit subjects alone depend on how well they were written.
82. **Projects in drafted files: your own projects and contributions, each under a head the server writes.** An `open_source` add-on is your own project or a contribution. A read decides from the commit share (decision 81), and a pull request someone else owns is always a contribution. You can switch it in the add-on form, and later reads keep your choice. In a resume, your own projects go under `## Projects` and contributions under `## Open Source Contributions`. The drafter writes `[PROJECT-n]` and the server writes the head: the name, the repo link when public, and up to 3 skills. Your own project gets one line saying what it is, plus at most 2 bullets for facts that prove a requirement of the posting. A contribution gets bullets about what you did. A check keeps each fact under its own project's head, and the server moves a head written in the wrong section to the right one. Tailoring a base CV may add up to 2 projects the CV lacks, with the same head. Letters, proposals and answers name projects as listed and never say you built or own a project you contributed to. Commit and file citations stay in the app. Why: the drafter got bare fact lines, so it guessed names and groupings, and a recruiter reading "built Viem" about a merged pull request would stop trusting the rest. See `docs/plans/project-citations.md`.
83. **Your own project is one paragraph that names its stack (amends 82).** In a resume, each of your own projects is its head, then one paragraph of 2 to 4 sentences with no bullets: what it is, what it does and what it is built with. Its head is only the name and the public repo link. Its stack moves into the paragraph. The drafter sees each own project's stack in the PROJECTS list, and a sentence that cites that project's facts may name those skills; any other skill still needs a fact that says it. The server joins whatever lines and bullets the drafter wrote under an own project's head into one paragraph, so a model that writes bullets anyway still gets the right shape. Each sentence keeps its own fact markers. Tailoring adds an own project the same way. Contributions keep the stack in their head and keep 1 to 3 bullets about what you did, since a paragraph would blur what was yours. Heads drafted before this change still parse. Why: a recruiter reads a side project as one piece of work, and the user asked for a short description with the stack instead of a list.

## Research findings

### Sources that allow automated reading

| Source | Access | Notes |
|---|---|---|
| Jobicy | Free JSON API, no key | Geo filters. Keep the Jobicy listing URL. |
| Himalayas | Free JSON API and RSS | Optional free key for higher limits. |
| RemoteOK | Free JSON API | Attribution and a link back are required. |
| We Work Remotely | RSS and JSON API with published terms | Attribution required. Applicants apply on WWR. Do not build a competing board. |
| Remotive | Free JSON API | Attribution required. At most 2 requests a minute and about 4 a day. Listings are delayed 24 hours. |
| Greenhouse, Lever, Ashby, SmartRecruiters, Recruitee, Workable | Public, unauthenticated job board APIs | Ashby has the best structured remote and location fields. Lever has `workplaceType`. Greenhouse location is free text. |

### Sources that forbid automated access

LinkedIn, Indeed (partner API only), JobStreet, Kalibrr, OnlineJobs.ph, Upwork (partner API only), Glassdoor (API retired), Wellfound and Toptal. Jobs from these come in through "add a job by link".

JobStreet's terms (updated 20 July 2026) were checked directly. §9(b) bans "any automated process, script, tool, bot, scraper" except through an API that SEEK provides, and §9(d) allows suspension of accounts that do this.

### Other findings

- **RA 10173 §3(h):** a person processing personal information for personal, family or household affairs is not a personal information controller. A shared multi-user copy would lose this exemption.
- **AI data use:** neither OpenAI nor Anthropic trains on API data by default. Anthropic's docs say conversation content is not retained by default, with 30-day retention for some covered models. The "7 days" figure from the research could not be confirmed.
- **Working for US clients:** contractor or employer-of-record (Deel, Remote.com, Oyster). A W-8BEN avoids the 30% withholding. Common payment rails are Wise, Payoneer and PayPal. BIR registration and the 8% income tax option apply on the Philippine side.
- **Stack:** Postgres.app bundles pgvector (checked directly). The TanStack blog shows the Start v1 release candidate from September 2025. The stable date comes only from a third-party post.
